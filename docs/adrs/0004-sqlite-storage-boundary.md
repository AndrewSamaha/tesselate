# ADR-0004: SQLite transaction and storage boundary

Status: Accepted for M001

`persistence::Database::commit_mutation` is the one durable mutation boundary. It uses an immediate SQLite transaction and accepts a nonempty batch of typed-at-construction `StateChange` records, expected revisions, canonical request/result, idempotency scope, and one event draft. The database checks all state preconditions before applying any changes, applies every state write, appends the immutable event with its monotonic sequence, links that event to each changed entity, and records the idempotency result before committing. Any failed precondition or write rolls the batch back. Replays return the stored result and event ID without applying a second state change; reusing a scoped key for another request is an error. The coordinator owns authorization and transition policy and supplies only already-authorized state changes.

SQLite uses WAL, foreign keys, a five-second busy timeout, and serialized writes through the owning `Database` handle. Idempotency requests are normalized recursively to sorted-key JSON before storage or comparison. Task updates preserve dependencies unless a replacement is explicitly provided; an empty replacement clears them. Event/message/entity pages return a cursor at the last item whenever the page is nonempty, including the final page, so a later poll starts after the last seen record. Event cursors are opaque random tokens persisted with their sequence position, so a client cannot invent a valid cursor by changing the sequence. The versioned migration is deterministic and rejects a database created by a newer schema. `load`, `list_entities`, `events_after`, and `messages_after` keep reads behind the persistence boundary.
