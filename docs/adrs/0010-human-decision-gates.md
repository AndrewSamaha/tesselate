# ADR-0010: Durable human decision gates

A human gate is a persisted `HumanDecision` record; it does not modify the task or run whose transition it guards. F04 calls `HumanTransitionGate` before committing the guarded transition. A pending, rejected, expired, or escalated decision returns a recoverable result, leaving unrelated work available. After approval, the caller retries the original operation and F04/F06 rerun their normal authorization and state checks.

When F01 has no human policy, or completion approval is disabled, run completion remains autonomous. When enabled, completion requires the `approve` choice. F06 calls `ReviewHumanGate` only for a high-severity deferral when its validated review policy requires approval. F07 creates a stable gate request identity for each run completion or finding/reason pair, so retries find the same durable decision. Resolving a gate does not bypass the guarded transition or its idempotency key.

Requests persist project/run/task scope, question, context, choices, requester, optional expiry and expiry action, current status, and resolution actor, choice, reason, and time. Expiry is materialized when the request is listed or its guarded transition is checked. `expire` stores `expired`; `escalate` stores `escalated`, which is visible to the supervisor/CLI request list. No background scheduler or notification channel is implied by this state transition; F09 owns CLI presentation.

Only supervisors create requests. Supervisors and CLI-authorized sessions may list and resolve them; session roles come from F05's validated `SessionContext`. Resolution validates an offered choice and nonempty reason. F02 commits request/resolution state, event, and idempotency result atomically. Reusing a mutation key with another payload conflicts. Reaffirming the same choice/reason by the same actor is recorded as an idempotent duplicate; a different resolution is rejected.
