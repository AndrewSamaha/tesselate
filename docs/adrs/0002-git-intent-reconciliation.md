# ADR-0002: Recoverable Git mutation intent

Status: Accepted for M001

Before invoking Git, persist an intent keyed by `(assignment_id, repository_id)`, including canonical repository and worktree paths, target branch, exact base commit SHA, owner, and `prepared` checkpoint. Advance to `mutation_started`, perform Git worktree creation from that exact base, persist observed repository identity/worktree path/branch/HEAD/cleanliness, and advance to `git_applied` then `recorded`, with the resulting `Workspace` attached. Workspace records its assignment ID so reassignment cannot overwrite history. A `conflict` checkpoint records ambiguous or mismatched observations and a recovery reason. Never overwrite an existing branch or path.

On retry, inspect Git metadata and filesystem. Record success only when branch, worktree path, repository identity, and HEAD match this intent. If no side effect exists, retry the same intent. If the matching worktree exists but database recording was interrupted, reconcile and record it. Mismatched or partial state is preserved for human inspection; cleanup does not silently repair it.

Workspace inspection is read-only and returns current HEAD, clean status, and changed paths. Commit capture takes an expected head SHA, verifies it is the observed worktree HEAD and descends from the recorded base, then records commits in `base..head` as `WorkspaceCommit` entities through one F02 mutation. The expected head makes the idempotent result stable. F03 implements `CommitAuthorLookup` from these captured workspace-to-commit records; missing refs fail closed, and the same commit captured in multiple workspaces maps conservatively to all associated owners.

Explicit cleanup refuses tracked, untracked, and ignored changes before any Git deletion, then persists `cleanup_started`. It removes only the recorded worktree and its branch, and records `cleaned` only once both are absent. A restart after Git removal but before the database checkpoint safely reconciles the missing pair; a mismatched pair is a conflict. Cleanup is never automatic.

SQLite and Git cannot share a transaction. This intent protocol makes the gap inspectable and retryable without claiming atomicity. F03 owns the command sequence and reconciliation behavior; F02 persists the checkpoints.

Assignment and run lifecycle changes must not race with the Git side effect. Creating a `prepared` intent compare-checks the currently observed Assignment and Run revisions. Advancing it to `mutation_started` atomically updates the intent and the unchanged Assignment and Run records at those exact revisions, advancing both revisions before any Git command. F04 refuses to release, supersede, submit, or disposition that exact assignment while its intent is `mutation_started` or `git_applied`; it likewise refuses a run-limit stop while an active assignment in that run has such an intent. If F04 prepared first, its Assignment or Run update makes F03's compare-and-update fail before Git; if F03 advanced first, F04's scan refuses the transition. Reconciliation after restart must move the intent to `recorded` or `conflict` to clear the refusal condition. F03 also refuses creation or reconciliation when the run is stopped. No separate lock bit is persisted, so recovery cannot leave an orphaned lock.
