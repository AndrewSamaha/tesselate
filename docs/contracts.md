# F00 shared contracts

This crate defines transport-neutral API types in `core` and a `Coordination` trait. MCP and CLI adapters authenticate a bearer credential through `SessionAuthenticator`, then pass the resulting opaque `SessionContext`; it has private fields and no wire serialization, so client-supplied actor or role fields cannot construct authority. The coordinator checks the bound session and revocation state for each operation. Mutations persist state, event, and idempotency record through `persistence::Database::commit_mutation` in one immediate SQLite transaction. Reusing a key within `(session_id, operation, key)` with the same canonical request returns the original result/event and `replayed=true`; a different request is `IdempotencyConflict`. State preconditions are checked in the same transaction as the state, event, and idempotency write. Coordination owns authorization and transition policy; persistence owns durable atomicity.

F02 exposes a nonempty batch of typed-at-the-boundary `StateChange` records with insert or expected-revision update semantics, `Database::load` and bounded `list_entities` reads, scoped `events_after` timelines, and typed `messages_after` reads. Omitted task dependency replacement preserves existing dependencies; `Some(vec![])` explicitly clears them. Each nonempty event/message/entity page returns a persisted opaque cursor at its last item, even when there is no next page, so clients can resume before later records arrive. Cursor tokens resolve to durable event sequence positions and arbitrary cursor values are rejected.

Run creation includes a goal. A created `Run` stores its UTC start time and a snapshot of validated project `WorkflowLimits` (duration, concurrent assignment, task retry, and review round caps). Terminal runs may include a `RunOutcome` reason and remaining task IDs. A `Task` stores its goal, attempt count, submitted commit IDs, and optional result. The run limits come from project configuration and cannot be supplied by a task creation request.

F01 parses project TOML into `ValidatedProjectConfig`, with `ConfiguredRepository` IDs and canonical repository roots, a canonical artifact destination, validated `WorkflowLimits`, `ReviewPolicy`, and `Option<HumanGatePolicy>`. Missing `[human]` is `None`; a configured `[human]` table is `Some(...)`, including when its only gate is explicitly false. F01 rejects unknown keys, duplicate IDs or canonical paths, non-root/non-Git repositories, zero workflow limits, fewer than two independent reviewers, and an artifact destination whose existing directory or nearest existing parent cannot accept a temporary write check. F02 owns persistence; F09 owns CLI input and argument handling.

Events use schema version 1, a monotonically increasing per-database `sequence`, UUID event identity, UTC timestamp, actor identity and role, optional project/run/task scope, stable snake-case event type, and structured JSON payload. Pagination is bounded and cursors are opaque, exclusive, sequence-backed tokens: a cursor after sequence N yields events with sequence greater than N in ascending order. Unknown or tampered cursors are errors. MCP uses namespace `tesselate.v1`, schema version 1, `ReadRequest` for reads, `MutationRequest` with a required idempotency key for caller-initiated mutations, and `ToolResponse` with explicitly tagged `{outcome:{status:"success"|"error",data:...}}`; error data is `{code,message,retryable}`. Unsupported schema versions return `unsupported_version`. The exact tool names are exported as `mcp::TOOLS`. Request `params` are tool-specific JSON; authenticated context is derived by the adapter and actor/role/session claims are rejected rather than accepted from those params. `Coordination` includes stable project/repository/agent/run/task discovery, run/task lifecycle and dispositions, available work, messages, workspaces, review rounds/findings, human decisions, timelines, and artifact lookup. Repository and agent lists are scoped to a project and use the standard bounded `PageRequest`/`Page<T>` cursor contract. `available_work` and human-request listing are discovery calls; deterministic run/human expiry may be materialized internally with the existing durable event/idempotency rules, without a client idempotency key or duplicate lifecycle event on repeated polling.

F08 runs one Tokio coordinator behind an owner-only Unix socket and starts an `rmcp` stdio process per harness session. Each tool publishes an explicit JSON Schema for its F00 `params` fields, required fields, nested objects, and enums; unknown fields are rejected at each object level by the coordinator before authentication/dispatch, then typed decoding validates values. Each adapter request carries the F00 versioned envelope and forwards it with a locally supplied credential; credentials never appear in tool params or responses. The coordinator authenticates each call through `SessionAuthenticator` and passes only the returned opaque `SessionContext` to `Coordination`. The local newline-delimited socket frame is an internal transport envelope, not an MCP request surface. Core errors and mutation event IDs remain in the versioned tool response. F09 owns process startup, credential-file presentation, and construction of the concrete `Coordination` implementation from F01–F07 services; F08 deliberately does not duplicate their policy or composition logic. The artifact discovery tool delegates to `Coordination::locate_artifacts`; F09 maps that operation to F10 `RunArtifactExporter::locate_run` while applying the bounded page contract and the core authorization policy.

Review rounds are persisted separately from reviewer results. `ListReviewRounds { task_id, page }` and `tesselate.v1.reviews.rounds.list` return all rounds for the task, including pending rounds with commit refs and prior finding IDs; `ListReviews` / `tesselate.v1.reviews.list` return only submitted reviewer results. Every review result or finding disposition increments the affected round revision. F06 completion checks return compare-only guards for the review rounds they evaluated; F04 includes those guards with the task completion state change in one F02 mutation. A concurrent review/disposition therefore either precedes completion and is included in policy evaluation, or changes a guarded revision and prevents completion. F06 writes also guard the task revision and accept reviews only while its status is `in_review`.

Review policy must require at least two independent non-author reviewers. F01 supplies the validated project policy; F03 supplies commit authorship lookup and remains responsible for verifying submitted refs against workspace/Git ownership. A finding is satisfied only after its persisted supervisor disposition; a finding marked fixed also must be linked into a later round with different commit refs before completion.

`CompleteRun` contains only the run ID and outstanding integration steps. The completion operation derives `Run.reviewed_commit_ids` from persisted task submissions whose commits have policy-satisfying persisted reviews. The caller cannot supply or override this list; completion fails if the review policy is not met. Final task dispositions are separately recorded with actor, reason, and event.

F10's `RunArtifactExporter` reads immutable events for one run through the bounded F02 event cursor and writes `runs/<run-id>/events.v1.jsonl`, `records.v1.jsonl`, and `timeline.v1.md` under the F01 validated artifact directory. Each event JSONL line is `{ "export_schema_version": 1, "event": <Event v1> }`, ordered by persisted event sequence. The related-record JSONL contains current run-scoped durable task, assignment, message, workspace, review, finding, disposition, human-decision, and run records so a standalone reader can resolve event references such as message bodies and review findings. Both JSONL formats have explicit export version 1. Markdown uses the same filtered event and record snapshots and stable local links for actor, task, review-round, repository, workspace, and commit references. Empty or nonterminal history is explicitly labeled incomplete. Repeat exports replace the same deterministic paths; temporary files and atomic rename make interrupted writes safe to retry. Export does not emit events or update authoritative workflow state. Sensitive-key and machine-local path fields are omitted recursively, credential-issuance event types are excluded, and current event producers must continue to keep credentials, secret configuration, and complete file contents out of event payloads. `RunArtifactExporter::locate_run` returns existing deterministic `ArtifactRef`s for F08 discovery; F08 remains responsible for authorization and paging through `Coordination::locate_artifacts`. F09 calls `export_run` from its CLI adapter. No export MCP tool is added; discovery retains `tesselate.v1.artifacts.locate`.

Credential bootstrap, Git crash recovery, and completion semantics are decided in ADR-0001 through ADR-0003. F01–F11 should implement against these contracts. This is interface scaffolding; feature behavior remains with its feature owner.

F04 task transitions are authorized by `coordination::tasks::TaskEngine`. F07's `HumanTransitionGate` receives project, run, optional task, typed from/to lifecycle state, and transition identity. Assignment capacity is computed across all active tasks in the run; available-work discovery is available to coders and supervisors and durably stops expired runs. Reassignment after an expired F05 lease preserves prior assignment history and never removes F03 workspaces. F05 supplies the exact durable lease entity and observed revision; renewal commits to that entity before it is treated as effective, and F04 passes the revision as a compare-only F02 `StatePrecondition` in the reassignment transaction. A guard conflict triggers a lease re-read and a safe refusal/retry. Before release, supersession, submission, or disposition ends an assignment, F04 refuses while its exact assignment has a Git intent in `mutation_started` or `git_applied`. The assignment revision update in the same F03 transaction that records `mutation_started` fences an F04 transition prepared before Git begins; if F04 ends the assignment first, F03's assignment compare-and-update fails before Git runs. Run-limit stops similarly refuse while any active assignment in that run has an in-flight Git intent; F03 advances both the intent and Run revision atomically before Git, so a previously prepared run stop fails its revision check. After restart, a run remains active until the in-flight intent is reconciled to `recorded` or `conflict`, then an expired run can be durably stopped. F03 reconciliation does not continue if the run is already stopped. Task dependencies unblock in the same persisted mutation that completes their prerequisite. Run duration and retry exhaustion persist a stopped run with its reason and remaining task IDs. Idempotency replay is resolved before state-dependent policy checks and rechecked after optimistic revision conflicts; the F02 commit transaction remains authoritative under races. See ADR-0005 and ADR-0002.

F03's `GitWorkspaceManager` accepts only registered canonical local repository roots and the current active assignment in an active run. Workspaces are keyed by `(assignment_id, repository_id)`; reassignment creates a distinct workspace and preserves old history. It persists `GitOperationIntent` checkpoints before and after explicit-argument Git commands, storing canonical repository/worktree paths, exact base SHA, branch, owner, observed Git state, result, and any conflict reason. The prepared intent insert checks the observed Assignment and Run revisions. The atomic `mutation_started` transition updates the intent plus unchanged Assignment and Run records at those same observed revisions, advancing both durable revisions before invoking Git. F04's terminal assignment transitions inspect intents for that exact assignment and refuse during `mutation_started` or `git_applied`; run-limit stops do the same for active assignments within the run. Assignment and Run revision fencing closes races with transitions that read before the intent. Reconciliation advances an interrupted intent to `recorded` or `conflict`, after which F04 can retry a stop or assignment transition; it refuses to create or reconcile while the run is stopped. A retry records success only when branch, worktree, repository identity, and base HEAD match the durable intent. Mismatched or partial state is preserved and reported for human inspection. `WorkspaceInspection` reports current repository-qualified HEAD, clean state, and changed paths. `CaptureWorkspaceCommits { workspace_id, expected_head }` records commits in `base..expected_head` through `WorkspaceCommit` entities and one event/idempotency result. F03's `CommitAuthorLookup` maps captured refs to their workspace owners (all owners if the same commit was captured in multiple workspaces) and rejects refs that were never captured, allowing F06 to enforce reviewer independence. Explicit cleanup stores `cleanup_started` before removal, refuses tracked, untracked, or ignored changes, and reconciles to `cleaned` only when both expected worktree and branch are absent. F08/CLI adapters call these F03 APIs rather than issuing Git commands. The stable MCP tool is `tesselate.v1.workspaces.commits.capture`.

F05 persists credential verifier digests and active/revoked/expired session state in the `credentials` entity table. Credential secrets are high-entropy coordinator-generated values; only their SHA-256 verifier digest is stored, and `IssuedCredential` redacts its secret in debug output. A successful first issuance returns `secret: Some(...)`; an idempotent retry returns the same session/actor IDs with `secret: None, replayed: true`, including a concurrent identical request that loses the commit race. Plaintext secrets are never stored to support replay. Bootstrap creates one pending verifier and only the bootstrap operation can consume it to create the first supervisor; supervisor issuance is separate and role-scoped. `SessionAuthenticator` reconstructs `SessionContext` from an active, unexpired credential; caller role claims never enter that context. F08/F09 own secure presentation and owner-only local file/socket handling. Credential revocation and explicit session expiry revoke associated assignment leases atomically.

An assignment lease is stored as `EntityKind::AssignmentLease`, keyed by the current F04 assignment record ID. The lease stores owner, session, expiry, and monotonic generation. It starts at the first renewal after assignment; no lease record is considered live or expired until this handshake succeeds. Each renewal updates the lease entity revision and checks the assignment revision in the same F02 transaction. F04 uses that lease revision as its compare-only reassignment guard. Defaults are a 12-hour session TTL and two-minute assignment lease TTL; deployment configuration can override them. Repository schema v2 adds durable credential and assignment-lease tables and migrates existing v1 databases.

Messages are stored in the scoped `messages` entity with event identity and timestamp in the append-only event stream. Event payloads contain the message ID and sender, not the body; reads use the persistent sequence cursor supplied by F02. Task-scoped messages inherit and validate their task's project and run, and remain available after disconnect or database restart. Credential values are never included in message events or coordinator diagnostics.

F07 persists each human request with its project/run/task scope, question, context, choices, requester, optional expiry/action, status, and optional resolution (choice, actor, reason, timestamp). `HumanRequest` requires at least two unique nonempty choices and pairs `expires_at` with `on_expiry` (`expire` or `escalate`). `tesselate.v1.human.request`, `.list`, and `.resolve` use the standard versioned MCP shapes. Supervisors may request decisions; supervisors and CLI-authorized sessions may list and resolve. Completion gates use F01 `completion_approval`; F06 calls the review hook only when its policy gates high-severity deferrals. A pending gate leaves the guarded transition unchanged; after approval the caller retries and normal transition/review checks run again. Expiration is durably applied on list or gate-check, and produces `expired` or `escalated`; escalation is visible in the request list, with CLI notification/presentation owned by F09. See ADR-0010.

A run-completion gate is keyed by the latest task/review evidence sequence for that run. Repeated attempts without changed task/review evidence reuse the same request, including a rejection; a later evidence event creates a new durable request while preserving the earlier decision. Human request/resolution events do not advance the evidence generation. After approval, F04 and F06 still validate and atomically commit completion.
