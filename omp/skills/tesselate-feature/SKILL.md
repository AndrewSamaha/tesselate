# Tesselate feature

Open an interactive OMP session from `~/Development` (select a local repo) or inside a repository beneath that workspace root. Request a feature naturally (for example, “Build a feature for this repo that …”), or use `/feature <goal>`. The extension collects acceptance criteria and constraints, then asks OMP to draft a specification. Clarify ambiguities before calling `tesselate_feature_start`. Confirm scope, the local base branch, and an explicit validation command for the worktrees named in the confirmation. Do not code in the initiating session.

Use `[validation].command` from the repository's `.tesselate.toml` when configured. Set `validation_override` only when the user explicitly requests a different command for this run. Otherwise, if no repo default exists, inspect the repository's build instructions and use a clear, safe build command for the affected target as `validation_command`. When the target or command is ambiguous, omit it so the extension can ask. Never start a run without the user's confirmation of the exact command.

The standard workflow launches one coder and at least two non-author reviewers in separate `omp -p` processes. For two independent approaches, use `/feature --workflow compare <goal>` or propose `workflow: "compare"` in `tesselate_feature_start` when the user asks for them. Each candidate starts at the same base and is reviewed and revised separately. The approved validation command runs in unprovisioned candidate validation worktrees, not agent worktrees. A fresh reviewer compares the two eligible candidates. Ask the human to select a winner, if any, even if only one qualifies. Only the selected commit fast-forwards onto the integration branch; validate there and export the run artifacts. No automatic push, PR creation, or merge into `main`.

The per-run handoff, worker session directories, process/log handles, and error are private under `<state_dir>/omp-runs/<run_id>/`. A pre-run intent is written before run creation so a crash can replay the same idempotency key. If interrupted, use `/feature resume` from the original repo (or select that repo from the workspace root); optionally append the full run UUID to target it directly. Resume requires no new specification or validation command. Inspect any reported mismatch before proceeding. When a coder or review budget is exhausted, OMP asks whether to try one more round, reset the task attempt count, or leave it for manual repair. Choose a repair only after inspecting the failure; manual repair leaves the run stopped or the comparison candidate failed for a later `/feature resume`. Use `tesselate status --watch` to see runs grouped by `run_id`, one line per agent with role, assignment, and status; active agents animate. Failed/interrupted integration validation requires an explicit inspected-log retry. Do not delete dirty worktrees to repair a failed run. Processes running under the same OS user are not a security boundary; role credential files prevent accidental authority mixing, not malicious local-file access.

Read the repository's AGENTS.md. For Bitwars, never merge into local `main` or start app/server/reset Redis in task worktrees. If a Tesselate per-repository provisioning policy exists, show the exact ignored paths for approval before copying them to the integration worktree only; absent optional paths are skipped, and coder/reviewer checkouts receive none. Do not execute workmux hooks or symlink ignored files. Generic repositories also require an explicit local base branch and a user-approved validation command. Never assume a package install or shared-service test is safe. If review, validation, provisioning, or a worktree identity check cannot be completed, leave the branch/run for recovery and report the exact obstacle.
