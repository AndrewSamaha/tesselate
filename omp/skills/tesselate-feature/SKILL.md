# Tesselate feature

Discuss the feature normally in OMP. Call `tesselate_feature_start` only when the user asks to delegate implementation to Tesselate and the goal, observable acceptance criteria, and constraints are clear. Ask about material ambiguities in chat, then pass the agreed spec directly; no `/feature` command is required. Use the current repository beneath `~/Development`, or let the tool ask which repository to use from the workspace root. The tool confirms the repository, scope, local base branch, workflow, and exact validation command before launching workers. `/feature <goal>` still opens the guided intake. Do not code in the initiating session.

Use `[validation].command` from the repository's `.tesselate.toml` when configured. Set `validation_override` only when the user explicitly requests a different command for this run. Otherwise, if no repo default exists, inspect the repository's build instructions and use a clear, safe build command for the affected target as `validation_command`. When the target or command is ambiguous, omit it so the extension can ask. Never start a run without the user's confirmation of the exact command.

At setup, choose UX design for changes to user or player flow, decisions, or feedback; UX checklist for a small tweak to an existing interaction; or no UX stage only if there is no user-facing change. Do not plan or code in the initiating session.

After approval, two independent read-only planners inspect the same base in separate checkouts. UX design adds a third read-only worker in parallel to propose the interaction, edge states, and checks. The supervisor selects one plan and reconciles it with the design, or writes a checklist in checklist mode. The supervisor may ask one worker for a targeted revision. If reconciliation is blocked, clarify the requirements and start a new run rather than resuming the unchanged spec.

The supervisor saves the selected architecture, rationale, and any agreed UX brief before coding. Coders and reviewers get the same brief. Resume reuses completed planning work without asking for a new UX decision.

The standard workflow then launches one coder and at least two non-author reviewers in separate `omp -p` processes. For two independent implementations of the selected plan, use `/feature --workflow compare <goal>` or propose `workflow: "compare"` in `tesselate_feature_start` when the user asks for them. Each candidate starts at the same base and is reviewed and revised separately. The approved validation command runs in unprovisioned candidate validation worktrees, not agent worktrees. A fresh reviewer compares the two eligible candidates. Ask the human to select a winner, if any, even if only one qualifies. Only the selected commit fast-forwards onto the integration branch; validate there and export the run artifacts. No automatic push, PR creation, or merge into `main`.

The per-run handoff, worker session directories, process/log handles, and error are private under `<state_dir>/omp-runs/<run_id>/`. A pre-run intent is written before run creation so a crash can replay the same idempotency key. If interrupted, use `/feature resume` from the original repo (or select that repo from the workspace root); optionally append the full run UUID to target it directly. Resume requires no new specification or validation command. Inspect any reported mismatch before proceeding. When a coder or review budget is exhausted, OMP asks whether to try one more round, reset the task attempt count, or leave it for manual repair. Choose a repair only after inspecting the failure; manual repair leaves the run stopped or the comparison candidate failed for a later `/feature resume`. When a resumed run completes, a completion report is written under the run directory and a completion message wakes the OMP session. Use `/feature status` or `/feature status <full-run-UUID>` to inspect the latest or a specific run without resuming it. Use `tesselate status --watch` to see runs grouped by `run_id`, one line per agent with role, assignment, and status; active agents animate. Failed/interrupted integration validation requires an explicit inspected-log retry. Do not delete dirty worktrees to repair a failed run. Processes running under the same OS user are not a security boundary; role credential files prevent accidental authority mixing, not malicious local-file access.

Read the repository's AGENTS.md. For Bitwars, never merge into local `main` or start app/server/reset Redis in task worktrees. If a Tesselate per-repository provisioning policy exists, show the exact ignored paths for approval before copying them to the integration worktree only; absent optional paths are skipped, and coder/reviewer checkouts receive none. Do not execute workmux hooks or symlink ignored files. Generic repositories also require an explicit local base branch and a user-approved validation command. Never assume a package install or shared-service test is safe. If review, validation, provisioning, or a worktree identity check cannot be completed, leave the branch/run for recovery and report the exact obstacle.
